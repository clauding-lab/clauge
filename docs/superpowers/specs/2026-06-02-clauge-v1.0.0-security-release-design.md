## 2. What the grounding pass corrected (read before implementing)

The code-grounding workflow verified each fix against HEAD and **overturned four assumptions** the plan inherited from stale code/comments:

1. **Windows external links are almost certainly NOT broken.** The `on_new_window` handler that shell-opens `http/https/mailto` has existed since **v0.4.4** (`windows.rs:126-148`, not platform-gated). 2. **`filePath` was never in `/api/export`.** The exporter uses a fixed 18-column whitelist (`exporter.js:9-28`) with no `filePath`. → "keep filePath in export" is a no-op; **do NOT add it to the export** (that would re-leak the path Fix 1b removes).
3. **The impersonation fix needs no secret/crypto** (see §5).
4. **`localhost` is a real dashboard origin**, not cosmetic — the extension popup points the dashboard link at `http://localhost:${port}/` (`extension/popup.js:43`). The CORS allowlist MUST admit both `127.0.0.1` and `localhost`.

## 3. Fix 1a — Lock the local server's CORS to the app's own origins

**Problem (review finding S2):** read endpoints use `origin: '*'` (`server.js:178-182`), so any website the user visits can `fetch()` Clauge's data cross-origin (project paths, shell-command names, usage stats).

**Verified facts:** all three product webviews fetch `/api/*` **same-origin** — the popover (`native_popover.rs:503`, `http://127.0.0.1:<port>/popover/index.html`), the dashboard (after `splash.js:32-34` redirects to `http://127.0.0.1:<port>/`), and the onboarding window makes no `/api` fetches (IPC only). The only cross-origin reader is the extension, and it only hits the **write** endpoint `/api/usage/ingest`, which has its own separate allowlist.

**Design:** replace `origin: '*'` inside `readOnlyCors` (`server.js:178-182`) with a **reflecting predicate**: allow iff the request `Origin` parses to scheme `http` AND host ∈ {`127.0.0.1`, `localhost`} (ANY port); otherwise emit no `Access-Control-Allow-Origin`. A missing `Origin` (same-origin simple GET) → no ACAO needed.

**Hard constraints (from the critic):**
- Change ONLY the `origin` field inside `readOnlyCors`. **Keep the per-path `READ_ONLY_API_PATHS` loop** (`server.js:159-185`) — do NOT switch to a global `app.use('*', cors())`, or it hijacks the separately-handled `/api/usage/ingest` OPTIONS preflight (`server.js:202-216`), breaking the extension write.
- Port must be a **wildcard within the loopback host** — the sidecar can land on a crash-respawn fallback port (3457+, `windows.rs:52-56`). A fixed `:3456` allowlist would break those.
- Do NOT add `tauri://localhost` / `http://tauri.localhost` — no API-fetching page runs from those origins.

**Open sub-decision (implementer):** confirm the pinned Hono `cors()` version, with an origin function, reflects the request origin when allowed and emits NO ACAO (not `'*'`/`'null'`) when disallowed/missing. Verify in a real DMG, not just dev (WebKit edge on missing-Origin).

**Blast radius closed:** drive-by websites can no longer read the local server.

## 4. Fix 1b — Trim leaked filesystem paths from responses

**Verified consumers:**
- `claudeDir` is emitted by `/api/health` (`server.js:231`) and `/api/config` (`server.js:529`). **No frontend reads either** (Settings/About reads only pid/subscriptionCost/pricing/version; the MAS connections "logs path" row uses a *different* field, `claude_code_logs.path` from IPC). The ONE reader of `config.claudeDir` is the local CLI `clauge config get` (`config-get.js:57` + test `config-get.test.js:88`).
- `filePath` is set on every cached session summary (`session-store.js:71`) and returned by `/api/sessions*`. **No frontend reads it** (verified zero readers repo-wide). Not in the export.

**Design:**
1. **Remove `claudeDir` from `/api/health`** (`server.js:231`) — zero consumers.
2. **Keep `claudeDir` in `/api/config`** — its only reader is the same-user local CLI, and after Fix 1a `/api/config` is no longer cross-origin-readable, so the path no longer leaks to websites. Dropping it would break a real CLI consumer + its test for no post-1a security gain. *(Rationale documented so a reviewer doesn't "tidy" it away.)*
3. **Remove `filePath`** by deleting the producer line `session-store.js:71` (verified safe — no internal or external readers). Do NOT strip it by `delete s.filePath` at the response handler — those objects are the **shared in-memory cache** (`session-store.js:72`); mutating them corrupts the cache. (If a future internal use of `filePath` appears, switch to building new objects at the `/api/sessions*` boundary instead.)
4. **`/api/export`: no change.** It never exposed `filePath`. Do NOT add it.

**Blast radius closed:** even a same-origin/local reader no longer sees the absolute home path or per-session `.jsonl` paths via `health`/`sessions`.

## 5. Fix 2 — Defeat sidecar impersonation by never trusting a server we didn't launch

**Problem (review gap S8 — the one the original review missed):** discovery adopts any server on `:3456` that echoes `{service:"clauge", version:<match>}` (`port_discovery.rs:73-83, 313-316`). The version is a public string, so a port-squatter can forge it; the app then points its webviews at the impostor's origin — and the dashboard webview carries the `__TAURI__` privileged command surface (`capabilities/main.json:6-7` grants IPC to `http://127.0.0.1:*`). So an impostor that wins the port can serve malicious JS into a privileged webview.

**Why no secret/crypto is needed:** discovery runs **before** the shell spawns its own sidecar, so a per-launch secret could never verify a pre-existing server (the trust target doesn't exist yet). The robust fix is to **stop adopting servers the shell didn't launch**, not to authenticate them.

**Design:**
- Change discovery so the shell **never returns `External` for an unverified pre-existing server**. Instead: if a Clauge-claiming server occupies `:3456`, treat it as an orphan/impostor — attempt `kill_pid_on_port(3456)` (reuses the existing path, `port_discovery.rs:321-329`) to reclaim the port from a **same-user** stale orphan, then **`SpawnAt`** our own sidecar. If the port can't be reclaimed (e.g. a different user's process — can't be killed), `listenWithRetry` binds a fallback (3457+) and the shell points webviews at **that** (our) port via `AppState`. The impostor on `:3456` is simply never loaded by our webviews.
- **Invariant:** the shell only ever points a webview (and `active-port`) at a port **its own spawn bound**. Verified the webview origin already follows `AppState.port` (`windows.rs:113-118`, splash redirect, popover reload), so this holds once adoption is removed.
- **Dev escape hatch:** gate "never adopt" to release builds. Under `cargo tauri dev` (or a `CLAUGE_ALLOW_EXTERNAL=1` env), keep adoption so the dev workflow of running `node server.js` separately still works. *(Verify the dev/hot-reload workflow doesn't depend on release-mode adoption.)*

**Honest limits / conceded threats (state plainly):**
- This defeats a **port-squatter** (including a *different user* on a shared Mac, who cannot kill our process or bind the port we hold). It does **not** defend against **same-user malware**, which can kill our sidecar and race the freed port on the one-shot discovery (`lib.rs:307-310`) or read anything we own — that threat is conceded by the whole loopback-only model and is unchanged.
- Discovery is **one-shot** today; this fix secures the initial point only. A future periodic re-probe (the `lib.rs:309` TODO) should re-apply the same "only trust a port we bound" rule.

**Touches:** `port_discovery.rs`, `lib.rs` (discovery→spawn routing). **No** `server.js`, no new dependency, no secret file, no crypto, no MAS-sandbox interaction.

## 7. Release — version bump + three-channel cut

**Version bump 0.9.10 → 1.0.0 (landmine #21 — all four in lockstep):**
1. `package.json` `version`
2. `src-tauri/tauri.conf.json` `version`
3. `src-tauri/Cargo.toml` `[package] version`
4. **`src-tauri/Cargo.lock`** (the `clauge` package entry) — run `cargo check --manifest-path src-tauri/Cargo.toml` and commit the regenerated lock. **This is the highest-probability failure:** the release "verify version triple" step (`release.yml:88-109`) does NOT check `Cargo.lock`, but `cargo test --locked` (`release.yml:154`) does, ~12 min into an irreversible tagged build. This exact gap sank v0.9.8.

**MAS:**
- `tauri.mas.conf.json` `bundleVersion` **5 → 6** (marketing version `CFBundleShortVersionString` auto-inherits 1.0.0 from `tauri.conf.json` — this file has no own version field).
- `scripts/build-mas-clean.sh:186` hardcodes the **helper** `CFBundleVersion` to `4` (already drifted vs build 5). **Template it from `bundleVersion`** (or set to `6`) to kill the recurring drift.
- Respect the signing order (landmine #27): build → wrap helper.app → inject `ITSAppUsesNonExemptEncryption=false` into the MAIN Info.plist **after build, before codesign** → sign helper → re-sign main → productbuild/productsign.
- **1.0.0 is a NEW App Store version record**, not a resubmission. v0.9.10 is accepted + live. Create a 1.0.0 version in ASC, attach build 6, confirm Trader Status still declared. *(Ignore the stale submission ID in `build-mas-clean.sh:338`.)*

**CHANGELOG:** add a `## [1.0.0]` section (top is currently `## [0.9.10]`); the release body is awk-extracted by header match (`release.yml:180-185`) — missing section = empty release body.

**Tag/sequence:** merge to `main` after a full `npm run check` (landmine #29 — `cargo fmt` is the first short-circuiting gate; any `.rs` edit from Fix 2 / the Windows comment must be `cargo fmt`'d), then push `v1.0.0`. CI builds the universal DMG (un-notarized, status quo) + Windows NSIS, signs the updater payloads with the existing Tauri key, and mirrors `latest.json` to gh-pages + the Homebrew tap. The MAS `.pkg` is built + submitted **manually** via the script (not in CI); channels are independent, so MAS can be submitted before or after the tag.

## 10. Honest limits & conceded threats (carry into the changelog/security notes)

- The local-server hardening assumes a **trusted single-user machine**; **same-user malware is conceded** (it can read what the user can and race a freed port). Fixes 1a/1b/2 raise the bar against *websites you visit* and *port-squatters (incl. other users on a shared Mac)*, not against malware already running as you.
- **Notarization (DMG) and Authenticode (Windows) are NOT in 1.0** — they're the next "signing" milestone. The DMG ships un-notarized exactly as v0.9.10 did; the App Store build is signed via the store identity as always.
