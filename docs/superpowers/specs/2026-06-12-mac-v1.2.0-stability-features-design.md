## Item 1 — Popover Quit button (and ⌘Q)

**Today:** `popover/popover.js::quitApp()` (~762-768) posts `{cmd:'quit'}` to the WKWebView's `clauge` script-message handler. `native_popover.rs::handle_script_message` (match ~198-241) implements only `open_dashboard` and `resize`; `quit` hits the catch-all and logs `unknown script message cmd=quit`. Both the ✕ Quit button and the popover's ⌘Q are dead — since the v0.5.0 native-popover migration. `ipc::quit_app` exists but is unreachable from the popover (raw WKWebView, no Tauri IPC) and has zero JS callers.

**Fix:** add a `"quit"` match arm in `handle_script_message` mirroring `menu_quit` (~283-288): `if let Some(app) = APP_HANDLE_REF.get() { app.exit(0); }`. Sidecar teardown + port-file removal already happen downstream in `lib.rs`'s `RunEvent::ExitRequested` (427-465). No frontend change; no IPC triple-registration (webkit channel, not Tauri IPC).

**Rider:** correct the stale header comment at `popover.js:5-6` that claims quit already works (becomes true once the arm exists — no JS edit, no sidecar rebuild).

**Not touched:** `openSettings`'s dead `cmd:'open_settings'` path (no caller since v0.9.4); the `quit_app` IPC command and its validator exemption; everything else in `native_popover.rs` (landmine #11 — transient behavior, transparency stack, size constants are deliberate).

**Verify:** manual macOS smoke — ✕ Quit and ⌘Q both exit cleanly (sidecar gone, port file removed). No E2E possible (landmine #9: tauri-driver has no macOS support).

## Item 2 — Keychain expiry re-read

**Today:** `src-tauri/src/keychain_cache.rs` caches `ClaudeCodeCreds` in a `Mutex<Option<…>>` forever; `invalidate()` (~75) has zero production callers. `connections::detect` (~140-155) checks `expires_at` on the cached blob every 30s poll — once expired, the Connections panel shows "OAuth token expired — re-run `claude /login`" indefinitely, even after Claude Code rotates the token in the Keychain. Recovery today is manual only (↻ → `refresh_credentials` IPC, or app restart). The *briefed* S1 ("401 reuses dead token") is unreachable — the cached token is never sent over the network; `anthropic_oauth::fetch_oauth_usage` (the only bearer-auth + 401-mapping code) has test-only callers. This fix addresses the live inverse bug.

**Fix:** inside `KeychainCache::get_or_load` — on a cache hit whose creds fail `keychain::is_expired`, drop the entry and re-read the Keychain **once** (return whatever the re-read yields; a still-expired re-read is cached and reported as before — no loop). Fixes every current and future consumer at the single choke point.

**Prompt safety** (the cache's reason to exist, `keychain_cache.rs:1-8`): the re-read fires only while creds are genuinely expired — the same read the manual ↻ performs today. No unconditional refresh-per-poll.

**Not touched:** the dormant `fetch_oauth_usage`/401→`TokenExpired` contract and its pinned test stay as-is for the future Arch-A caller; Keychain item names (landmines #4/#14); no sidecar involvement (token custody is entirely Rust-side).

**Verify:** TDD red-first via the existing `with_reader` injection — (a) expired-hit triggers exactly one re-read and returns fresh creds; (b) non-expired hit does NOT re-read (prompt-safety pin); (c) expired-hit with a still-expired re-read reports expired without looping. UI effect: Connections panel self-heals within one 30s poll of a token rotation.

## Item 3 — HTTP timeouts (Rust parent + Node CLI)

**Today (recon inventory):** three production Rust loopback calls use bare `reqwest::get` with **no timeout** (reqwest has no default): `ipc.rs:470` `proxy_fetch` (no live JS caller, but registered); `native_popover.rs:669` tray-percent poller (30s single-threaded loop — one hung connection freezes the menu-bar % forever); `icloud_publish.rs:111-112` snapshot GET (5-min loop — a hang wedges iPhone publishing indefinitely **and** blocks the loop's shutdown check; sits directly on the iPhone-staleness path from the 2026-06-11 wedge). Two sites already build per-call clients with timeouts (`ipc.rs:572` health 2s; `port_discovery.rs:48` probe 1s). A 10s shared client exists (`anthropic_oauth.rs:13` `OAUTH_CLIENT`) but serves only dormant code. The Node CLI duplicates a 2s `AbortController` helper verbatim in `lib/cli/_toggle.js` and `lib/cli/config-get.js`; the sidecar's LiteLLM call already uses an 8s `AbortController`.

**Fix (Rust):** new `src-tauri/src/http_client.rs` exposing `LOCAL_CLIENT: Lazy<reqwest::Client>` with a 5s default timeout (`once_cell` + `reqwest` already in Cargo.toml — **no new dependencies**). Adopt at the three bare call sites; consolidate the two per-call builders onto it with per-request `RequestBuilder::timeout` overrides keeping their existing 2s/1s values. `proxy_fetch` stays method-pinned GET (ipc.rs threat-model comment). Do not restructure the sibling-loop topology (landmines #10/#36): the `icloud_publish.rs` timeout goes inside `publish_once`; the poller timeout inside the poller body.

**Fix (Node CLI):** new `lib/http.js` ESM helper `fetchWithTimeout(url, init, timeoutMs)`; adopt in `lib/cost-calculator.js:49` (8s), `lib/cli/_toggle.js:25` (2s), `lib/cli/config-get.js:31` (2s) — collapses three bespoke `AbortController` copies, values preserved. Bundled via import — no `sea-config.json` ASSETS entry; confirm with `npm run test:sea`. (This is the **server-side outbound** helper — distinct from Item 6's **browser-side** frontend timeouts.)

**Verify:** unit tests where extractable (client config, helper behavior, per-request overrides); `cargo test` + `npm test` + full `npm run check`. Manual hang-check optional (dev `node server.js` needs `CLAUGE_ALLOW_EXTERNAL=1`, landmine #31).

## Item 4 — iCloud sync-health (upload confirmation)

**Goal:** an honest signal that the snapshot the Mac publishes is actually reaching iCloud — and therefore the iPhone. The 2026-06-11 wedge was invisible because a *successful* `NSFileCoordinator` write proves nothing about delivery: the Mac wrote the file fine, but Apple's iCloud daemon silently never uploaded it. Only the file's post-write iCloud resource values reveal this.

**Today:** `icloud_publish.rs` publishes every 5 min — `run()` (43-78) → `publish_once()` (83-140) GETs the snapshot from the sidecar, stamps seq + writerId, and calls `write_snapshot_coordinated` (`icloud_writer.rs:94-158`) inside `spawn_blocking` (126-133). It persists `icloud_snapshot_seq` (SEQ_KEY) + `icloud_writer_id` (WRITER_ID_KEY) but **no last-published timestamp**. `run()` logs `Ok(seq)` → `info`, `Err` → `debug` (72-75). There is **no `PublishError` enum** (the publisher returns `Result<u64, String>`) and **no `SyncHealth` type** anywhere. The write path uses pure `objc2` / `objc2-foundation` 0.3.2 / `block2` (no Swift helper); container resolution is cfg-branched — MAS via `URLForUbiquityContainerIdentifier` (51-56), DMG via the direct `~/Library/Mobile Documents/…` path (65-73).

**Fix A — read upload status (`icloud_writer.rs`):** after the coordinated write, read the target file's iCloud resource values via `NSURL::resourceValuesForKeys_error([NSURLUbiquitousItemIsUploadedKey, NSURLUbiquitousItemUploadingErrorKey])` — a **safe** binding in the pinned `objc2-foundation` 0.3.2, all required features (`NSString/NSArray/NSDictionary/NSError`) already enabled, **no new deps**. This runs inside the existing `spawn_blocking` on the same thread as the write (landmine #35: `Retained<NSURL>` can't cross an `.await`), inside `publish_once` (landmines #10/#36: do **not** restructure the sibling loop or fold into the sidecar supervisor).
- **Honest timing:** immediately after a fresh write, `IsUploaded` legitimately reads `false` (the file is queued for the daemon). So a naive "confirm uploaded" check would log a false failure every tick. The honest read is the **previous** cycle's file state, taken at the *start* of each `publish_once` (eventually-consistent, no sleep). The real wedge detector is `UploadingError != nil`; `IsUploaded` is the last-known-delivered flag.
- **Privacy (landmine #34):** do not echo Apple's raw `UploadingError` string (it can read "Couldn't access your iCloud account…"). Map to a generic, calm message: "iCloud upload issue — check that iCloud Drive is signed in and working."

**Fix B — persist + expose (`icloud_publish.rs`, `lib.rs`, IPC):**
- Add a persisted `lastPublishedAt` (+ last-known upload state / error-present flag) beside SEQ_KEY/WRITER_ID_KEY in the tauri-store; stamp on each `publish_once`.
- Introduce a typed `SyncHealth { state, last_seq, last_published_at, detail }` mirroring `connections.rs::ConnectionStatus`/`ConnectionState` exactly (serde lowercase string tags). `SyncHealthState ∈ { ok, pending, error, stale, unknown }` — `pending` = written, upload not yet confirmed; `error` = `UploadingError` present (wedge); `stale` = no confirmed upload in ~24h; `unknown` = publishing disabled / no data yet.
- New `#[tauri::command] get_sync_health` returning `Result<SyncHealth, String>`, reading the **persisted** state (cheap; no synchronous container touch on the IPC call). **IPC triple-registration (landmine #1):** `lib.rs` `invoke_handler!` (380-401), `build.rs` `APP_COMMANDS` (12-43), `capabilities/main.json` permissions (9-38, add `allow-get-sync-health`); CI validator `scripts/validate-ipc-triple-register.cjs` must pass. Add a `ClaugeBridge.getSyncHealth()` method to `popover/lib/tauri-bridge.js` (the **source** copy; regenerate the gitignored `public/popover/` mirror via `npm run build:sidecar` — landmine #30).
- Promote the `icloud_publish.rs:74` publish-`Err` log `debug` → `warn` (a hard local-write failure should not be invisible at the default filter while success logs `info`).

**Fix C — UI (dashboard only; the popover can't host IPC — landmine #28):**
- **Settings row:** add a 5th `.connection-row` "iCloud sync to iPhone" in Settings → Connections (`public/index.html`, `data-set-panel="sync"`, 423-485), driven by the existing `connections.js::applyRow` pattern (179-193) — `data-state` green/amber/red dot + `.conn-status` text — polled on the existing 30s connection cycle via the new `getSyncHealth()`. States: ✓ synced (last upload *Nm* ago) / ⏳ uploading / ⚠ upload failing / ⚠ no upload in 24h+.
- **Minimal banner (net-new, on-brand):** a small notice at the top of the dashboard's main view, shown **only** when `state ∈ { error, stale }`, reusing the existing color/glass tokens (no existing banner/toast component — this is the one piece of net-new UI). Concise message + the actionable advice; hidden when healthy.

**Scope:** both DMG + MAS (`icloud_*` are `#[cfg(target_os = "macos")]`, both flavors). MAS needs no new entitlement (reading resource values on the already-resolved ubiquity container).

**Verify:** TDD on the pure parts — `SyncHealthState` derivation from `{ uploadOk, uploadError, ageSeconds }`; the 24h staleness boundary; the serde shape (mirrors a `connections.rs` test). The native resource-value read is exercised behind the `spawn_blocking` seam where extractable; manual macOS smoke: induce a wedge (iCloud sign-out, the 2026-06-11 repro) → banner + red row within one poll; healthy → ✓ row, no banner.

## Item 5 — SWR / honest freshness (popover + dashboard)

**Today:**
- **Popover** (`popover/popover.js`): `refresh()` (669-722) wraps each fetch in `.catch(() => null)` (681-688); `plan = usage?.plan ?? {}` (692) → renderers coerce `?? 0` → **0% rings**. A single failed refresh **destroys** the displayed data, and the freshness subhead (`renderHeaderSubhead` 579-597, called @695) still says "Updated just now". No last-good cache; the popover has **no** `.dot-live`. Separately, `renderRoutines` (417-429) has **no null-gate** — a dropped Daily Routines bucket phantoms "0 of 15 runs" (@424), unlike the gated `renderDesign` (401-415, gate @406-408).
- **Dashboard** (`public/app.js`): `refreshAll` (1180-1229) **already** keeps last-good — `state.data` is assigned only on full success (1204); any rejection hits `catch` (1223) and leaves it. But on failure the `.dot-live` keeps **pulsing** (lies "live") and "synced ago" **freezes** (only recomputed on success). The anti-flicker machinery already exists: `setTextIfChanged` (162-173), structural-update-on-shape-change (334-340), `updatePlanMeta` preserving `.dot-live` (520-537), and a not-live dot variant (`app.js:282` / `styles.css:921` = `animation:none` + grey).

**Fix (popover):**
- Add a module-level `lastGoodUsage` cache; on `null`/abort from a fetch, render from last-good instead of zeros (keep-last-good).
- Honest freshness: never show "just now" after a failed refresh. Keep the data's real age (`ingestedAt`) and apply a muted/"stale" treatment to the subhead when the **last fetch failed**. The cue is the existing freshness subhead text + a dim treatment — **not** a net-new pulsing dot (the popover has none; keep it lean).
- Add the missing `renderRoutines` null-gate, copying `renderDesign`'s pattern.

**Fix (dashboard):**
- On a failed refresh, set `.dot-live` to not-live (grey, `animation:none` — reuse the existing variant) so it stops lying.
- Track `lastSuccessAt`; recompute the "synced ago" via `fmtAgo` (87-99) against it on **every** tick, including failures, so the timestamp keeps **aging** ("5m ago" → "6m ago") instead of freezing.
- Preserve `.dot-live` across refreshes via the existing surgical-update path (landmine #22 — never `innerHTML`-rebuild the live region).

**Two orthogonal, honest signals:** *data age* (`ingestedAt` — how old the underlying usage data is) stays as-is on both surfaces; the *live / not-live* cue reflects *fetch success* (is the app still talking to its backend). They are independent.

**Verify:** TDD where pure — last-good substitution on `null`; the routines null-gate; the not-live + aging logic (given `lastSuccessAt` + `now` → correct "synced ago" + dot state). Playwright `MutationObserver` to confirm zero `childList` churn on the dashboard live region across a failed refresh (landmine #22 pattern). Manual: kill the sidecar mid-session → popover keeps rings + shows stale, dashboard dot greys + timestamp keeps aging; restore → both recover.

## Item 6 — Frontend fetch timeouts + overlap guard + popover boot-order

**Today:** two bare browser-side fetch wrappers with no `AbortController` — dashboard `api()` (`app.js:138-144`) and popover `fetchJson()` (`popover.js:198-202`); no shared frontend module. The popover boot-order does `await refresh()` (832) **then** `setInterval` (833): a hung first fetch (no timeout) strands `#po-loading` forever. The dashboard has an exponential-backoff `initialLoad` (1280-1302, up to 30s) for the 100ms–8s cold-start race.

**Fix:**
- Add a ~5s `AbortController` timeout in **both** wrappers (duplicate ~4 lines each — a shared helper would cross the popover/public facade boundary + the HTML-facade load-order validator; not worth it). `clearTimeout` in `finally`; an abort throws, which both wrappers already propagate.
- **Route into keep-last-good (depends on Item 5):** the dashboard is already safe (abort → `catch` → `state.data` retained); the popover is safe **only after** Item 5's last-good cache lands. This is the sequencing the original v1.1.1 deferral was protecting — adding fast-fail timeouts before keep-last-good would make the popover's wipe-to-0% fire *more* often. In this combined release, Item 5 ships **before/with** Item 6, dissolving the conflict.
- **Overlap guard:** an in-flight flag so a slow refresh can't stack on the next interval tick (popover `setInterval` @833; dashboard 60s @1326-1335).
- **Popover boot-order:** with the 5s timeout the first fetch can no longer hang forever; ensure a failed first refresh lands on a recoverable state (existing recovery path 813-816) and the interval still starts.
- **Cold-start budget:** the 5s per-attempt timeout must not regress the dashboard's backoff cold-start (up to 30s; 8s+ possible) — an abort is treated as a normal retry by the backoff, so per-attempt 5s is fine, but verify the first-load path doesn't abort a legitimately slow cold start prematurely (cross-project webview-sidecar-race rule).

**Verify:** unit where pure (the wrapper aborts at the budget; the overlap guard rejects re-entrancy). Manual: simulate a hung sidecar → the popover spinner resolves to a recoverable/stale state within ~5s (no permanent spinner); no overlapping refreshes; a slow cold start still succeeds.

## Item 7 — sevenDay schema-drift tripwire

**Today:** `lib/usage-store.js` computes `unknownSevenDayKeys` (113-115) against a `KNOWN_SEVEN_DAY_KEYS` set (81-92, 10 keys); it is returned on `GET /api/usage` `plan` (`server.js:620-629`) and rides into the iOS snapshot (`snapshot.js:225-228`) at `SNAPSHOT_SCHEMA_VERSION = 1`. **Nothing reads it.** `CHANGELOG.md:255` falsely claims it is "Logged so future Anthropic renames are visible" — grep finds zero log statements in JS or Rust. (The Rust mirror getter `anthropic_oauth.rs:123` is dormant/test-only.) Its purpose: catch a brand-new Anthropic weekly bucket (as "Claude Design" once was) before it silently makes the dashboard incomplete.

**Fix:**
- **Structured log** in the Node sidecar where the field originates — on ingest (`server.js:583-618`, after `normalizePlanUsage` @593), emit a structured warning when `unknownSevenDayKeys` is non-empty (lighter touch than the dormant Rust getter).
- **Quiet Settings line** (dashboard): `renderSettings()` (`app.js:866-887`) reads `state.data.usage?.plan?.unknownSevenDayKeys` and renders a new muted `set-row` near the About row (`index.html:397-401`) **only** when non-empty: "1 unrecognized usage category — an update may track it." No banner; only an app update can act on it.
- Correct the false `CHANGELOG.md:255` claim once the log lands (consider an AGENT_LEARNINGS entry: a CHANGELOG asserted a behavior never wired).
- **No schema bump** — read-only of an existing schema-1 field (landmine #37: a bump is a cross-repo contract that would strand every iPhone user until a matching clauge-ios build ships).

**Verify:** unit — the structured log fires iff `unknownSevenDayKeys` is non-empty; the Settings line renders iff non-empty. Manual: inject a fake unknown `seven_day_*` key → log + Settings line appear; remove → both gone.
