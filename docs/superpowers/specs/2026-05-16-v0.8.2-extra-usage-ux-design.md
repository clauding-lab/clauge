# Design: Extra Usage card UX when Anthropic gates the feature (Clauge v0.8.2)

**Date:** 2026-05-16
**Author:** brainstorming session (post-v0.8.1 ship + Clauge Sync v0.1.9 dig)
**Status:** approved, ready for implementation plan
**Target version:** v0.8.2
**Scope:** Both platforms (macOS DMG + Windows NSIS). Same distribution channel as v0.8.0/v0.8.1. Pure UX polish.
**Sequencing:** v0.8.1 (shipped 2026-05-16, splash + wizard install step) → **v0.8.2 (this spec)** → TBD (likely Clauge Sync v0.1.9 Web Store publish + v0.8.3 if Anthropic ungates the API in the meantime)

---

## Problem

The dashboard's EXTRA USAGE card currently shows `$0.00 / not configured` even when the user has the extra-usage feature toggled on in claude.ai's settings page and has spending against it. The reason: claude.ai's `/api/organizations/{uuid}/usage` endpoint returns:

```json
"extra_usage": {
  "is_enabled": false,
  "monthly_limit": null,
  "used_credits": null,
  "utilization": null,
  "currency": null,
  "disabled_reason": "org_level_disabled_until"
}
```

The Clauge parser at `lib/usage-store.js:65-85` correctly reads `is_enabled: false` and produces `extraUsage: { enabled: false, ...all nulls }`. The dashboard's `renderFinanceSide` at `public/app.js:288-314` then falls into the `else` branch and renders the "not configured" misleading copy.

**User-facing misread:** the user thinks they need to set up extra usage when in fact they have it set up, and Anthropic's API has temporarily gated their org. The Clauge card hides the actual reason.

The `disabled_reason` field IS in the API response (`"org_level_disabled_until"` confirmed via the user's claude.ai DevTools fetch on 2026-05-16). The parser just doesn't propagate it forward.

## Decision

Pass `disabled_reason` through the parser to the dashboard, render a third state for the EXTRA USAGE card that shows the gated reason instead of "not configured." Three rendering states:

| Condition | Dollar value | Bar | Status text |
|---|---|---|---|
| `extra.enabled === true` | `$19.60` | red/orange filled, % shown | `$19.60 of $10.00 cap` (existing behavior, unchanged) |
| `extra.enabled === false && extra.disabledReason` | `—` | gray (no fill) | mapped reason text, e.g. `Temporarily gated by Anthropic` |
| no `extra_usage` block, or `enabled === false && !disabledReason` | `$0.00` | empty | `not configured` (existing behavior, unchanged) |

Reason → text mapping is a small lookup table with a generic fallback:

```javascript
const DISABLED_REASON_TEXT = {
  'org_level_disabled_until': 'Temporarily gated by Anthropic',
};
function disabledText(reason) {
  return DISABLED_REASON_TEXT[reason] || 'Disabled by Anthropic';
}
```

Forward-compatible: unknown `disabled_reason` values surface a generic message instead of either erroring or leaking the raw enum string to users.

**Considered and rejected:**

- **Show the raw `disabled_reason` enum** (e.g. literally render "org_level_disabled_until"). Cons: leaks Anthropic's internal vocabulary. Unfriendly. Rejected.
- **Show $19.60 from claude.ai's settings UI instead of `—`.** The settings page exposes spending data the API doesn't currently return. We could fetch the settings page HTML and scrape, but that's brittle (settings page DOM changes faster than API) and contradicts our existing API-only data contract. Rejected.
- **Hide the EXTRA USAGE card entirely when gated.** Cons: removes the user's only diagnostic signal that the gate exists. Rejected.

## Scope

### Modifies (frontend)

- `lib/usage-store.js::normalizePlanUsage` — add a `disabledReason` field to the returned `extraUsage` object when `extra.disabled_reason` is present on the raw response. Pass through camelCased. No other normalization (the value is a string enum from Anthropic, not a number we'd convert).
- `public/app.js::renderFinanceSide` — new branch: if `extra && !extra.enabled && extra.disabledReason`, render the gated state (dollar value `—`, gray bar, mapped reason text). Add the `DISABLED_REASON_TEXT` lookup constant at module scope alongside other constants.
- `public/styles.css` — new `.extra-bar--gated` class for the grayed/neutral bar variant; the existing `.extra-bar` styling stays put and toggles via a state class.
- `public/index.html` — no change. The existing bar element will receive the `--gated` class via JS `classList.toggle`.

### Modifies (tests)

- `test/usage-store.test.js` — add three test cases:
  1. `extra_usage.is_enabled: true` → `extraUsage.enabled: true` and no `disabledReason` (regression guard for the existing happy path)
  2. `extra_usage.is_enabled: false, disabled_reason: 'org_level_disabled_until'` → `extraUsage.disabledReason: 'org_level_disabled_until'`
  3. `extra_usage.is_enabled: false, disabled_reason: null` → no `disabledReason` (falsy-pass-through guard)

### Unchanged (verified)

- `lib/usage-store.js::normalizeBalance` (prepaid balance) — unrelated to extra_usage, untouched.
- `extension/background.js` — extension already passes the raw response through to the server, doesn't filter `disabled_reason`. No change required.
- `server.js::/api/usage/ingest` — stores the raw response in `record.raw.extra_usage`. The parser at line 475 reads it via `normalizePlanUsage`. No server change required.
- `public/index.html` EXTRA USAGE markup (around lines 80-95 in the dashboard). Existing `.extra-bar`, `#extra-used`, `#extra-cap`, `#extra-bar`, `#extra-pct`, `#extra-currency` IDs all stay.
- Auto-updater plumbing, gh-pages mirror, build matrix, all unchanged.

## Open questions

- **Other `disabled_reason` values.** We've only observed `'org_level_disabled_until'` empirically from one org. Anthropic may use other enum values (e.g. `payment_required`, `tier_not_eligible`, `policy_violation`). The generic fallback "Disabled by Anthropic" handles unknowns gracefully — and we can extend `DISABLED_REASON_TEXT` as we learn the catalog. No action required for v0.8.2.
- **Should we surface `disabled_reason` in any other UI?** Just the EXTRA USAGE card for now. The Settings → Connections rows talk about authentication state, not feature gates. Keep scope tight.

## Risks

- **Anthropic ungates the user mid-cycle and the API starts returning `is_enabled: true`.** No risk — that path is the existing happy state, untouched by this change.
- **Anthropic deprecates `disabled_reason` or renames it.** The parser already uses `??` operators and the dashboard treats missing `disabledReason` as state 3 (fallback to "not configured"). Forward-safe.
- **Existing v0.8.1 dashboard breaks if the parser change is incompatible.** Mitigated by: the `disabledReason` field is an OPTIONAL property added to `extraUsage`. Old dashboards (pre-v0.8.2) that don't know about it simply ignore the extra field — JSON serialization-tolerant.

## Success criteria

- User with `extra_usage.is_enabled: false, disabled_reason: "org_level_disabled_until"` in their `/api/usage` response sees the EXTRA USAGE card render with dollar value `—`, gray bar (no fill), status text "Temporarily gated by Anthropic" / "USD".
- User with `extra_usage.is_enabled: true` (future state once Anthropic ungates) sees the existing $XX.XX / X% of cap rendering, unchanged.
- User with no `extra_usage` block or `is_enabled: false` without `disabled_reason` sees the existing `$0.00 / not configured` rendering, unchanged.
- Unit tests in `test/usage-store.test.js` cover all three states.
- `cargo test --locked --lib` continues to pass (zero Rust changes, regression guard only).
- `npm test` covers the new `disabledReason` test cases plus existing usage-store tests.
- v0.8.2 GitHub Release published with Mac DMG + Windows NSIS installer + signed `latest.json`. Mac auto-update from v0.8.1 succeeds.

## Ship strategy

Single branch on top of v0.8.1 (`clauding-lab/load-last-session` is the active workspace branch; v0.8.2 work continues there OR forks to a new branch — implementer's call). One PR or direct fast-forward to main matching the v0.8.0/v0.8.1 pattern. One CI cycle (single matrix build). Tag v0.8.2 after Mac dashboard smoke confirms the new card renders.

Subagent dispatches use Opus on every call (per memory `feedback_subagent_model.md`). Same implementer + spec reviewer + code quality reviewer pattern.

## Out of scope for v0.8.2 (named so they don't drift in)

- **Clauge Sync v0.1.9 Web Store publish.** Manual step the user performs in Chrome Web Store dashboard. Not a code change. Track as a separate user task.
- **Server-side preserve-last-good for `rawClaudeBalance`.** Defense-in-depth alongside extension v0.1.9. Consider for v0.8.3 if v0.1.9 in the wild doesn't fully eliminate the empty-card issue.
- **Stale indicator on CLAUDE.AI BALANCE card.** Companion UI to v0.1.9's last-good cache. Consider for v0.8.3.
- **WebView2 cookie capture investigation** for Architecture A on Windows. Multi-day, deferred indefinitely.
- **Edge add-ons store listing for Clauge Sync.** Separate publish workflow, deferred.
- **Authenticode signing for Windows.** ~$300-500/yr EV cert, deferred until install volume justifies.
- **System tray icon on Windows.** Architectural limit (no dynamic-text tray on Windows). Acceptable status quo.
- **Mac dev `cargo tauri dev` smoke.** Pending since v0.8.0; never blocking, just sanity check. Run when convenient.
