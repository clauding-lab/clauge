# Design: Keychain UX + first-launch wizard + v0.7.x debt cleanup (Clauge v0.7.2)

**Date:** 2026-05-14
**Author:** brainstorming session (post-v0.7.1 same-day cut)
**Status:** approved, ready for implementation
**Target version:** v0.7.2
**Scope:** macOS DMG flavor only — same distribution channel as v0.7.0 / v0.7.1. No Apple Developer enrollment, no Mac App Store work, no Windows work.
**Sequencing:** v0.7.1 (shipped) → v0.7.2 (this spec) → v0.8.0 (MAS flavor + Architecture A data plumbing) → v0.9.0+ (Windows)

## Problem

Two distinct user-visible problems plus a stack of carried-forward technical debt from v0.7.x:

**Problem 1 — Keychain prompts every dashboard open.** After installing v0.7.0/v0.7.1, the macOS Keychain prompt ("Clauge wants to use your confidential information stored in 'Claude Code-credentials'") appears repeatedly during normal use. Two root causes:

- *Cause 1A — ad-hoc-signed app:* The DMG flavor is built without an Apple Developer ID signing certificate. `codesign -dv /Applications/Clauge.app` reports `Signature=adhoc`, `TeamIdentifier=not set`, `Sealed Resources=none`. macOS Keychain ACLs ("Always Allow this app") bind to a code signing identity; ad-hoc-signed apps have no stable identity. As a result, the "Always Allow" button may not appear at all (the user sees only "Allow" / "Deny"), and even if it does, the trust does not persist across app launches.
- *Cause 1B — polling re-reads on every IPC call:* `src-tauri/src/connections.rs::detect()` calls `keychain::read_claude_code_credentials()` on every invocation. `get_connection_status` IPC fires every 30 seconds via dashboard polling, plus on window focus and `connections-updated` events. Even with Always-Allow working, this hits Keychain Services ~120 times per hour.

The "no Always Allow visible" symptom dominates the user's perception, but caching alone would reduce the prompt count by ~99% within a session. Cause 1A's permanent fix (Apple Developer ID + notarization) is already on the v0.8.0 plan as Task 12 (the MAS submission gate). Bundling it into v0.7.2 would double-pay the enrollment + CI plumbing cost. v0.7.2 therefore addresses **frequency** via in-memory caching and **comprehension** via a first-launch wizard, deferring **persistence** to v0.8.0.

**Problem 2 — No guided first-launch experience.** After dragging Clauge.app into Applications and double-clicking, the user is presented with a menu-bar icon and a dashboard that immediately triggers the unexplained Keychain prompt. There is no "Welcome to Clauge / here's what's about to happen / click Always Allow when prompted" surface. For the only end-user (the developer themselves) this is mildly annoying; for any future users it would be the make-or-break first-impression moment.

**Problem 3 — Carried-forward v0.7.x technical debt.** Several items deferred from v0.7.0 / v0.7.1 implementation now have free capacity in v0.7.2's scope:
- `Expired` keychain state surfacing (compositor currently collapses to `NotInstalled`)
- Architecture A retry-loop ceiling (`claude_ai_session.rs` polls forever if cookie capture fails)
- Errno-based keychain error mapping (currently string-matches against `e.to_string()`)
- Magic-number constants (extension freshness window, keychain account default, reqwest timeout)
- Shared `reqwest::Client` with timeout (three `TODO(v0.8.0)` markers)
- Popover JS-not-running fix (already on `main` as commit `07fca20`; rides v0.7.2 unchanged)

## Decision

Ship v0.7.2 as a focused **UX + debt-cleanup release**. Two new building blocks plus six mechanical fixes:

1. **In-memory keychain cache** (`src-tauri/src/keychain_cache.rs`). Held in `AppState`. Reads-on-demand, caches forever, refreshes on explicit invalidate (from OAuth 401 caller) or explicit refresh (from new "Refresh" button in Settings → Connections).
2. **First-launch onboarding wizard.** Separate Tauri `WebviewWindow` named `onboarding`. Four screens: Welcome / Keychain expectation-setting (with mock dialog illustration + "Always Allow" arrow) / Other permissions (notifications, login items, optional claude.ai) / Ready to connect. Fires on first launch BEFORE any keychain access happens. Gated by a new `onboarding_completed` flag in `tauri-plugin-store` (recommended approach — see "Open implementation questions" for the alternative of sharing the existing `first_launch_done` autostart flag).
3. Carryover-debt items (mechanical):
   - Expired-state surface in `connections.rs::detect()` + `connections.js` label
   - Retry-loop ceiling in `claude_ai_session.rs` (60s @ 1.5s = 40 attempts)
   - Errno-based keychain error mapping (`security_framework::base::Error::code()`)
   - Magic-number constants extracted to module-level consts
   - Shared `reqwest::Client` via `OnceCell` (anthropic_oauth + claude_ai_session)
   - Popover fix rides along (already merged; no design work)

**Mac App Store flavor, Apple Developer ID signing, notarization, and Architecture A data plumbing all remain explicitly out of scope and ride v0.8.0.** The v0.8.0 plan and spec will be amended to remove the carryover-debt items from their scope (since they ride v0.7.2 now).

## Components

### Keychain cache

`src-tauri/src/keychain_cache.rs` (new module, ~80 lines including tests).

```rust
use std::sync::{Arc, Mutex};
use crate::keychain::{read_claude_code_credentials, ClaudeCodeCreds, KeychainError};

pub struct KeychainCache {
    inner: Arc<Mutex<Option<ClaudeCodeCreds>>>,
}

impl KeychainCache {
    pub fn new() -> Self {
        Self { inner: Arc::new(Mutex::new(None)) }
    }

    /// Returns cached creds if present; else reads keychain + caches.
    /// Multiple concurrent callers serialize on the mutex — only one
    /// keychain read happens per cache miss.
    pub fn get_or_load(&self) -> Result<ClaudeCodeCreds, KeychainError> {
        let mut guard = self.inner.lock().map_err(|e| {
            KeychainError::Framework {
                code: 0,
                message: format!("cache lock poisoned: {}", e),
            }
        })?;
        if let Some(creds) = guard.as_ref() {
            return Ok(creds.clone());
        }
        let creds = read_claude_code_credentials()?;
        *guard = Some(creds.clone());
        Ok(creds)
    }

    /// Force a fresh read; replaces the cache. Triggers macOS prompt.
    pub fn refresh(&self) -> Result<ClaudeCodeCreds, KeychainError> {
        let creds = read_claude_code_credentials()?;
        match self.inner.lock() {
            Ok(mut guard) => { *guard = Some(creds.clone()); }
            Err(e) => log::warn!("cache lock poisoned on refresh: {}", e),
        }
        Ok(creds)
    }

    /// Clear the cache. Next get_or_load triggers a fresh read.
    pub fn invalidate(&self) {
        match self.inner.lock() {
            Ok(mut guard) => { *guard = None; }
            Err(e) => log::warn!("cache lock poisoned on invalidate: {}", e),
        }
    }
}
```

**Thread-safety note:** The mutex serializes concurrent `get_or_load()` calls. The first caller through the gate reads the keychain (triggering the macOS prompt if uncached); subsequent callers block on the mutex briefly and return the cached value. This means concurrent dashboard polls + a manual Refresh click don't race into multiple prompts.

**Error-variant note (implementation-time refinement):** The sample above synthesizes a `KeychainError::Framework { code: 0, message: ... }` for the lock-poisoned case, using a magic `0` because there's no real OSStatus. The implementer should either (a) extend `KeychainError` with a dedicated `LockPoisoned` variant, or (b) keep the existing string-form `Framework(String)` variant and reserve the structured `{ code, message }` form for actual security-framework errors. Decision deferred to writing-plans / implementation; the cache contract (the four-method public API) does not change either way.

const { invoke } = window.__TAURI__.core;
let currentStep = 1;

function showStep(n) {
  document.querySelectorAll('.wizard-step').forEach(s => s.classList.remove('active'));
  document.querySelector(`[data-step="${n}"]`).classList.add('active');
  document.getElementById('wizard-progress').value = n;
  currentStep = n;
}

document.addEventListener('click', async (e) => {
  if (e.target.matches('[data-next]')) showStep(currentStep + 1);
  if (e.target.matches('[data-back]')) showStep(currentStep - 1);
  if (e.target.matches('[data-skip]')) {
    try { await invoke('wizard_skip'); } catch (err) { console.error(err); }
  }
  if (e.target.matches('[data-connect]')) {
    try { await invoke('wizard_complete'); } catch (err) {
      console.error('wizard_complete failed:', err);
      // The Rust side handles store-write failures gracefully (logs warn,
      // closes window). If Keychain prompt itself fails (Deny), the dashboard
      // surfaces it next.
    }
  }
});

## Data flow

### First launch (cold path)

```
1. User opens /Applications/Clauge.app
2. Tauri runtime starts; lib.rs::run().setup() runs
3. Setup reads `first_launch_done` from tauri-plugin-store
4. Flag MISSING → spawn `onboarding` window (URL: /onboarding/)
                  (do NOT spawn dashboard yet; do NOT call cache.get_or_load() yet)
5. Wizard renders Step 1
6. User clicks through Steps 1-3 (no IPC, just step navigation)
7. Step 4: user clicks "Connect"
   → IPC `wizard_complete()`:
     - Marks `first_launch_done = true` in store
     - Calls `cache.refresh()` (THIS triggers the macOS Keychain prompt)
     - Closes the wizard window
     - Spawns / surfaces the main dashboard window
8. User sees Keychain prompt, clicks "Always Allow"
9. Dashboard opens, Connections panel populates with cached creds
   (no further prompts during this session — cache hit on every poll)
```

### First launch — skip path

```
7'. Step 4: user clicks "Skip for now"
    → IPC `wizard_skip()`:
      - Marks `first_launch_done = true` in store
      - Does NOT call cache.refresh() (no Keychain prompt)
      - Closes wizard, spawns dashboard
8'. Dashboard opens, Claude Code row shows "Not Installed" (compositor returns
    NotInstalled because cache is empty + read hasn't happened)
9'. User clicks ↻ button next to Claude Code row → IPC refresh_credentials
    → Keychain prompt fires → user clicks Always Allow → cached → row updates
```

### Steady state (every dashboard open after first launch)

```
1. App launches; setup reads `first_launch_done` → flag PRESENT → skip wizard
2. Dashboard opens immediately
3. Connections panel polls `get_connection_status` IPC every 30s
4. Each IPC call: connections::detect() → cache.get_or_load() → cache MISS
   → single keychain read (triggers Keychain prompt because ad-hoc-signed +
     Always-Allow doesn't persist) → cached
5. Subsequent polls (same session): cache.get_or_load() → cache HIT → no read
```

**Net effect:** ~120 keychain reads per hour → 1 read per app launch.

### OAuth 401 path (token expired naturally)

```
1. Caller (TBD; v0.8.0 ingest path or future direct-Rust health probe) calls
   anthropic_oauth::fetch_oauth_usage(access_token) with cached token
2. Anthropic returns 401 → fetch_oauth_usage returns Err(OAuthError::TokenExpired)
3. Caller catches TokenExpired → calls cache.invalidate()
4. Next connections::detect() → cache MISS → fresh read
5. If fresh read returns valid creds (user re-ran `claude /login`):
   → compositor returns Authenticated → green dot
6. If fresh read returns creds with is_expired == true:
   → compositor returns Expired → amber dot + "Expired" label
   → user prompted (via tooltip or banner) to run `claude /login`
```

Note: For v0.7.2, no caller currently invokes `fetch_oauth_usage`. The 401-path is wired but unexercised until v0.8.0's Architecture A data plumbing (or until a Rust-side health probe lands). For v0.7.2 we ship the cache.invalidate() call path so it's ready; no live test possible without the calling site.

### Manual refresh path

```
1. User clicks ↻ button in Connections panel
2. Frontend → IPC refresh_credentials → cache.refresh()
3. Keychain read fires (triggers prompt) → cached
4. Rust handler emits app event `connections-updated`
5. Frontend listener catches event → re-polls get_connection_status → UI updates
```

## Error handling

| Failure | Detection | Recovery |
|---|---|---|
| Keychain entry missing (user never ran `claude /login`) | `KeychainError::NotFound` from `keychain::read_claude_code_credentials` | Compositor returns `NotInstalled` state → red dot + "Sign in with `claude /login`" CTA. Cache stays empty (no failure-cached state). |
| User clicked "Deny" on Keychain prompt | `KeychainError::AccessDenied` (errSecUserCanceled = -128) | Cache stays empty. Compositor returns `NotInstalled`. Toast: "Keychain access denied. Click ↻ to try again." Wizard window has already closed; user must use ↻ button. |
| Token expired naturally | `OAuthError::TokenExpired` (401 from Anthropic) | Cache.invalidate() → next read → if expired, compositor returns `Expired`. |
| Wizard window fails to spawn | Tauri returns error from `WebviewWindowBuilder::build()` | Log warn, set `first_launch_done = true` anyway (don't loop on broken wizard), fall through to direct keychain access on first IPC. Wizard is a UX enhancement, not a hard dependency. |
| `first_launch_done` flag write fails | tauri-plugin-store error | Log warn; wizard will re-show on next launch. Annoying but not broken; idempotent on Connect-click side (re-running wizard_complete is safe). |
| Keychain read fails with unknown OSStatus | `KeychainError::Framework { code, message }` | Log error with code; toast generic "Keychain access failed (code N)"; do NOT cache the failure (next attempt re-reads). |
| Cache mutex poisoned | (extreme; shouldn't happen) | `log::warn!`; treat as cache-miss path; do best-effort recovery. |

**Crucial invariant:** the cache only ever holds a successfully-read `ClaudeCodeCreds`. Failed reads are NOT cached, so retry-on-next-call is automatic.

## Open implementation questions

(Not blockers for spec approval; resolved during the writing-plans phase or per-task during implementation.)

1. **Autostart timing vs wizard.** The existing `first_launch_done` flag in `lib.rs:81` is used to auto-enable Launch-at-Login on first launch. The wizard introduces a NEW first-launch concept. Two options:
   - Share the flag: both autostart-enable AND wizard gate on the same flag. Wizard runs first; on completion, autostart enables. Simpler.
   - Separate flags: `first_launch_done` for autostart, `onboarding_completed` for wizard. Allows future "Re-run onboarding" feature to reset the wizard flag without flipping autostart back on (in case user had intentionally disabled it).
   - **Decision (folded into spec above):** separate flags. The autostart flag is permanent; the wizard flag could conceivably be reset by a future "Re-run onboarding" feature without side effects on autostart.

2. **Wizard window size.** 560×640 is a guess. Implementation may need to adjust after rendering with the actual content + system fonts.

3. **`refresh_credentials` rate-limiting.** If the user spams the ↻ button, do we rate-limit? Initial answer: no — Mutex serialization in `cache.refresh()` already collapses concurrent calls. The button is also disabled during in-flight refresh on the frontend side.

4. **Logging level for wizard events.** First-launch flow is rare and high-signal; recommend `log::info!` for the spawn/complete/skip transitions.

5. **`open_onboarding` IPC command.** Listed in scope as "optional stretch." Decision deferred to implementation: if scope permits in the v0.7.2 cycle, add it (small surface — 1 IPC + 1 button in Settings); otherwise carry to v0.8.0.
