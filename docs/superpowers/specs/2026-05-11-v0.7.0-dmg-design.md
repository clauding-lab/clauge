# Design: Hybrid Auth on macOS, DMG-only (Clauge v0.7.0)

**Date:** 2026-05-11
**Author:** brainstorming session (continuation of 2026-05-09 v0.7.0 design; rescoped 2026-05-11)
**Status:** approved, ready for implementation
**Target version:** v0.7.0
**Scope:** macOS only, DMG flavor only — hybrid auth (Architecture B primary, Architecture A fallback). Mac App Store distribution deferred to v0.7.1.
**Sequencing:** v0.7.0 (this spec, DMG-only) → v0.6.0 (Windows port with unified architecture) → v0.7.1 (MAS flavor, parallel side workstream)

**Supersedes:** `docs/superpowers/specs/2026-05-09-v0.7.0-hybrid-mas-design.md` (combined DMG+MAS spec). Per the 2026-05-11 re-sequencing decision (saved in project memory `project_release_sequencing.md`), MAS work is split into a separate v0.7.1 cycle to remove Apple-review risk from v0.7.0's critical path. v0.5.1 dropped entirely.

## Problem

Clauge v0.5.0 → v0.6.0 ships data acquisition via three paths today:
- **Local JSONL parsing** of `~/.claude/projects/**/*.jsonl` (Claude Code CLI usage; the killer feature)
- **Clauge Sync browser extension** (claude.ai plan rings, prepaid balance — rides the user's existing browser session)
- **Bookmarklet fallback** (manual one-shot sync via the user's bookmarks bar)

The desktop app holds no auth of its own. It's a passive display surface that depends on a browser extension scraping claude.ai. For a typical Clauge user with Claude Code CLI installed, there is no zero-config onboarding path — they must install a Chrome extension AND keep claude.ai signed in in a specific browser profile.

Recent research (HN comment on a Show HN thread for `Usage for Claude` MAS app + open-source clones) revealed two viable architectures used by competing Claude usage trackers:

- **Architecture B**: read the OAuth access token Claude Code CLI already stores in macOS Keychain under service name `Claude Code-credentials`, call `api.anthropic.com/api/oauth/usage` directly. Zero login UI. Works for users with Claude Code CLI installed (Clauge's primary audience).
- **Architecture A**: embed a WKWebView, user signs into claude.ai inside the app, capture session cookies, call `claude.ai/api/organizations/{uuid}/usage`. Established pattern (Hayek's `Usage for Claude` MAS app runs this in production). Works for all users including claude.ai-only ones.

Combining these as a hybrid — B primary, A fallback — gives a zero-config UX for the typical Claude Code user, while leaving the existing extension as a stable third option for browser-only and Windows users.

## Decision

Build a hybrid macOS auth/data architecture in the DMG flavor. The app gets two new independent data paths:

- **Architecture B (primary):** read Claude Code's OAuth token from macOS Keychain → call `api.anthropic.com/api/oauth/usage` directly.
- **Architecture A (fallback):** in-app WKWebView modal → user signs into claude.ai → capture `sessionKey` cookie → call `claude.ai/api/organizations/{uuid}/usage`.

The browser extension is **kept**, not deprecated — it remains a third independent connection for Windows users, browser-only users, and Mac users who prefer it.

**Mac App Store distribution is the v0.7.1 follow-up.** v0.7.0 is DMG-only — no Apple review, no sandbox, no security-scoped bookmark. This keeps v0.7.0's critical path off Apple's calendar. v0.7.0 ships when the implementation work is done; v0.7.1 ships when Apple approves.

## Scope

**Adds (Rust / Tauri):**
- `src-tauri/src/keychain.rs` (new): macOS Keychain Services wrapper to read the `Claude Code-credentials` entry; extract OAuth access + refresh tokens; return a structured `ClaudeCodeCreds` struct.
- `src-tauri/src/anthropic_oauth.rs` (new): bearer-token-authenticated HTTP client for `api.anthropic.com` endpoints; primary call is `GET /api/oauth/usage`; refresh-token flow if access token expired; falls through with `Result::Err` on auth failure.
- `src-tauri/src/claude_ai_session.rs` (new): WKWebView-based login modal (Tauri WebviewWindow); cookie capture; session-cookie persistence in Keychain Services under `com.clauding.clauge.claude-ai-session`; bearer-cookie-authenticated calls to `claude.ai/api/organizations/{uuid}/usage`.
- `src-tauri/src/connections.rs` (new): unified state machine over the three auth surfaces (Claude Code keychain / claude.ai webview session / browser extension heartbeat); exposes status to dashboard via existing IPC pattern.
- `src-tauri/Cargo.toml`: `security-framework = "2"` dependency (gated `[target.'cfg(target_os = "macos")'.dependencies]`).
- `src-tauri/entitlements.dmg.plist` (new — was implicit before): non-sandboxed entitlements for the existing direct-download flavor. Makes the entitlements posture explicit so v0.7.1's MAS variant can be a clean overlay.

**Adds (frontend):**
- `public/connections.js` (new) + Settings → Connections panel (rebrand of existing claude.ai sync card): three independent rows (Claude Code CLI, claude.ai web, Browser extension).
- Connection-aware install banner: only renders when none of the three claude.ai-data paths are active. Any one going positive auto-hides it.

**Modifies:**
- `src-tauri/src/lib.rs`: setup branch reads connection state from `connections.rs` and routes accordingly.
- `src-tauri/tauri.conf.json`: adds explicit `bundle.macOS.entitlements: "entitlements.dmg.plist"` so the flavor is explicitly configured.
- `server.js`: existing `/api/usage/ingest` POST handler stays; new internal-only IPC route or direct in-process write path for the keychain-piggyback and webview-session paths (they don't go through HTTP — Rust calls Anthropic, writes the result into the same shape the existing usage-store consumes).

**Unchanged:**
- All existing JSONL parsing (`lib/parser.js`, `lib/aggregator.js`, etc.) — the data model and per-session logic stay; only the file-read mechanism is unchanged in v0.7.0 (MAS-flavor sandbox-scoped read comes in v0.7.1).
- Browser extension (Clauge Sync) — kept at v0.1.7. Not deprecated. (v0.5.1's auto-detect work was dropped; the dashboard's existing extension-detection — if any — is unchanged.)
- `npx clauge` browser dashboard path — unaffected.
- Windows port from v0.6.0 — completely orthogonal; sequenced after v0.7.0.
- Tauri auto-updater for the DMG flavor — unchanged.

**Out of scope (moved to v0.7.1):**
- MAS-flavor sandboxed build (entitlements, two-flavor build infrastructure)
- Cargo `mas` feature flag (introduced in v0.7.1, not v0.7.0)
- `tauri.mas.conf.json` overlay
- `src-tauri/src/security_scoped_bookmark.rs` (MAS-only module)
- Apple Developer setup, App Store Connect listing, Transporter upload
- App Store reviewer notes about cross-app keychain entitlement
- "Check for Updates" → MAS Store redirect logic
- First-launch grant-access banner for `~/.claude/projects/`
- 4th Settings → Connections row ("Claude Code logs" via security-scoped bookmark)
- CI matrix row for MAS-flavor build

**Out of scope (deferred to v0.8.0 or later):**
- Windows hybrid auth (Windows Credential Manager + WebView2) — v0.6.0 (rescoped) absorbs this
- Microsoft Store submission — v0.8.0+
- Linux — out of scope as before
- Refresh-token flow for cases where Claude Code's keychain entry doesn't include a refresh token — fall through to Architecture A modal

## Architecture

### Decision tree at app launch

```
Clauge launches
  │
  ▼
connections.rs::detect()
  ↓
1. Probe macOS Keychain for "Claude Code-credentials"
   ├─ Found, token valid → mode=KEYCHAIN_CC, skip webview
   ├─ Found, token expired → attempt refresh
   │    ├─ refresh succeeds → mode=KEYCHAIN_CC
   │    └─ refresh fails → mode=NEEDS_LOGIN, fall through to step 2
   └─ Not found → mode=NEEDS_LOGIN, fall through to step 2
  ↓
2. Probe Tauri store for stored claude.ai session cookie
   ├─ Found → mode=CLAUDE_AI_SESSION, use cookie
   └─ Not found → mode=NEEDS_LOGIN
  ↓
3. Probe extension heartbeat
   ├─ Recent → mode=EXTENSION (existing path)
   └─ Stale/absent → keep mode from step 2
  ↓
Dashboard renders Settings → Connections panel reflecting all three states.
On NEEDS_LOGIN, banner offers "Sign in to claude.ai" CTA → Architecture A modal.
```

Multiple modes can coexist (e.g., user has Claude Code installed AND extension running). The `connections.rs` module composes them; the freshest data source wins for any given metric.

### Architecture B — Keychain piggyback (primary)

**File:** `src-tauri/src/keychain.rs`

**Dependency:** `security-framework = "2"` (Rust wrapper around macOS Security.framework). Gated by `[target.'cfg(target_os = "macos")'.dependencies]`.

**Read flow:**
```rust
use security_framework::passwords::get_generic_password;

pub fn read_claude_code_credentials() -> Result<ClaudeCodeCreds, KeychainError> {
    let blob = get_generic_password("Claude Code-credentials", "")?;
    serde_json::from_slice(&blob).map_err(KeychainError::Parse)
}

#[derive(Deserialize)]
pub struct ClaudeCodeCreds {
    pub access_token: String,
    pub refresh_token: Option<String>,
    pub expires_at: Option<String>, // ISO 8601
    // ... other fields ignored
}
```

First read of the entry triggers the standard macOS Keychain access prompt. User clicks **Always Allow** to make subsequent reads silent.

**API call:** `anthropic_oauth.rs`:
```rust
pub async fn fetch_oauth_usage(token: &str) -> Result<PlanUsage, OAuthError> {
    let client = reqwest::Client::new();
    let res = client
        .get("https://api.anthropic.com/api/oauth/usage")
        .bearer_auth(token)
        .header("anthropic-version", "2023-06-01")
        .send().await?;
    if res.status() == 401 {
        return Err(OAuthError::TokenExpired);
    }
    res.json().await.map_err(Into::into)
}
```

**⚠ Empirical verification gap (Phase 1 of plan):** the exact response shape of `/api/oauth/usage` is the OSS-community-documented endpoint (HN thread, hamed-elfayome's tracker). Phase 1 starts with a one-shot fetch + inspect to verify the response includes Session/All-models/Sonnet/Opus utilization fields equivalent to what `claude.ai/api/.../usage` returns today. If the response is materially different from what Clauge's UI expects, the data-mapping layer in `aggregator.js` adapts.

**Note on MAS:** the cross-app keychain entitlement (`com.anthropic.ClaudeCode`) is NOT needed in v0.7.0 — non-sandboxed DMG apps can read other apps' keychain entries with user permission (the standard Keychain prompt). The entitlement question is purely a v0.7.1 MAS concern.

### Architecture A — In-app WKWebView login (fallback)

**File:** `src-tauri/src/claude_ai_session.rs`

**Trigger:** `connections.rs::detect()` returns `NEEDS_LOGIN` AND user clicks "Sign in to claude.ai" in the dashboard banner OR Settings → Connections panel.

**Flow:**
1. Open a new Tauri `WebviewWindow` named `auth-claude-ai`, modal-style:
   - URL: `https://claude.ai/login`
   - Size: 520×720
   - Decorations: false (custom title bar matching dashboard style)
   - Skip taskbar: true
2. User signs in normally (Google / email / passkey)
3. The webview navigates to claude.ai's homepage post-login. Detect via `webview.on_navigation` — if URL host is `claude.ai` and path is `/` or `/chats`, login succeeded.
4. Tauri's `WebviewWindow::cookies(url)` API extracts cookies for `claude.ai` origin. Pull `sessionKey` (Anthropic's claude.ai session cookie name).
5. Persist cookie to Keychain Services under `service = "com.clauding.clauge.claude-ai-session"`, `account = user_email_or_claude_user_id`.
6. Close the auth window; trigger `connections.rs::detect()` to refresh; dashboard re-renders.

**Cookie-authenticated API calls:** subsequent calls to `claude.ai/api/organizations/{uuid}/usage` from Rust set `Cookie: sessionKey=<value>` header; also set `Origin: https://claude.ai` and `Referer: https://claude.ai/` to look browser-shaped.

**Cookie expiry / Cloudflare challenge handling:**
- `claude.ai` sessions typically last 30+ days. On 401/403 from the API, mark session expired; surface "Re-authenticate" CTA in Settings.
- If a 200 response body is HTML containing `cf-chl-bypass` or similar Cloudflare-challenge markers, re-open the auth window — navigating in WKWebView solves the challenge in-context, refreshes the cookie. Same dance as Hayek's `Usage for Claude` handles in production.

**⚠ Empirical verification gap (Phase 3 of plan):** Tauri 2.x's `WebviewWindow::cookies(url)` API may or may not return cookies marked `HttpOnly`. If not, fall back to detecting the post-login URL pattern and persisting a session marker only (without the cookie value), then re-authenticating via fresh webview navigation on each fetch (Hayek's pattern). Verification happens during Task 7 implementation.

### Settings → Connections UI (v0.7.0 — 3 rows)

Rebrands the existing "claude.ai sync" Settings panel to **"Connections"**. Three rows in v0.7.0 (a 4th row "Claude Code logs" is added in v0.7.1 for MAS-flavor users):

```
┌─ Connections ──────────────────────────────────────────────┐
│                                                            │
│  Claude Code CLI    🟢 Authenticated                       │
│  via macOS Keychain (Claude Code-credentials)              │
│  [Reconnect]  [About this connection →]                   │
│                                                            │
│  claude.ai web      ⚪ Not signed in                       │
│  Sign in to see plan-ring data even without Claude Code    │
│  [Sign in to claude.ai]                                    │
│                                                            │
│  Browser extension  ⚪ Not detected                        │
│  Optional. Useful for browser-only setups.                 │
│  [Install Clauge Sync →]                                  │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

Each connection is independent. No "primary auth" gating — the dashboard composes data from whichever sources are active. The freshest data wins per-metric (plan rings: keychain B beats webview A beats extension; per-session analytics: JSONL only).

The existing extension install banner becomes connection-aware: only shows for users who have no claude.ai data path active (no keychain B, no webview A, no extension). One of the three becoming positive auto-hides the banner.

## Decisions made (v0.7.0-specific)

| # | Decision | Reason |
|---|---|---|
| 1 | Hybrid (B primary, A fallback), not A-only | B is zero-config UX for typical Clauge user (Claude Code installed). A handles claude.ai-only users. |
| 2 | DMG-only in v0.7.0; MAS deferred to v0.7.1 | Removes Apple-review risk from critical path. DMG flavor ships when implementation is done, regardless of Apple verdict. |
| 3 | Browser extension is KEPT, not deprecated | Serves Windows users + browser-only users + power users who prefer it. Extension code is small + stable; ongoing maintenance cost is low. |
| 4 | `Settings → Connections` panel; each connection independent | Users can have any combination of (keychain CC / webview claude.ai / browser extension). No "primary auth" gating UX — composability over magic. |
| 5 | Cargo `mas` feature flag deferred to v0.7.1 | v0.7.0 doesn't ship MAS; adding the flag now creates unused infrastructure. Introduce it in v0.7.1 when the MAS-only modules land. |
| 6 | Explicit `entitlements.dmg.plist` in v0.7.0 | Makes the DMG flavor's entitlements posture explicit (non-sandboxed). Sets up the symmetric overlay structure for v0.7.1's MAS entitlements. |
| 7 | Endpoint `api.anthropic.com/api/oauth/usage` accepted on faith from OSS-community evidence | HN comment + hamed-elfayome's tracker confirm the endpoint is in use by published apps. Phase 1 of implementation verifies response shape before locking the data-mapping layer. |
| 8 | v0.5.1 (extension auto-detect) dropped | Per 2026-05-11 re-sequencing. The extension-detection banner work no longer fits — most v0.7.0 users won't need the extension at all. Constituency for the banner shrinks too far to justify the work. |
| 9 | Windows hybrid + Microsoft Store explicitly deferred | v0.6.0 (rescoped) absorbs the Windows-side architecture work. v0.7.0 stays macOS-only. |
| 10 | Tauri auto-updater unchanged for DMG | DMG flavor continues to receive v0.7.x → v0.8.x updates via the existing GitHub Releases + minisign-signed `latest.json` flow. No change to update mechanism. |

## Open questions / known unknowns (⚠ verify gates)

These are the same gates the original combined spec identified, all of which resolve within day 1-2 of implementation. None block design.

- **⚠ `api.anthropic.com/api/oauth/usage` response shape** — verified during Phase 2 Task 6 first-fetch, not pre-design. Plan accommodates a data-mapping shim if response differs from claude.ai's.
- **⚠ Refresh token availability in Claude Code's keychain entry** — depends on Claude Code's auth implementation; if the entry is access-token-only (no refresh), the token's lifetime forces an A fallback every time the access token expires. Worst case the user re-runs `claude /login` periodically; tolerable for v1.
- **⚠ Tauri 2.x WebviewWindow `cookies(url)` API behavior with HttpOnly cookies** — needed for Architecture A's cookie capture. Plan has a fallback (Hayek's pattern: re-navigate the webview on each fetch instead of persisting the cookie value).
- **Universal vs Apple-Silicon-only build** — DMG flavor stays universal (lipo-merged), unchanged from v0.6.x. Verify during Phase 6 that the SEA sidecar's `clauge-server-universal-apple-darwin` continues working.

**Moved to v0.7.1 (NOT v0.7.0 concerns):**
- Apple's review verdict on cross-app keychain entitlement
- App Store Connect listing approval timeline
- Whether Apple approves the security-scoped bookmark flow
- Sandbox compatibility of the SEA sidecar
