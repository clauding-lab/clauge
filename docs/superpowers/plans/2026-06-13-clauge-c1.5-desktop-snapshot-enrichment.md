## Goal

Make the Mac PUBLISH two OPTIONAL forecast blocks into its iCloud analytics snapshot so the iPhone can enrich its on-device forecasts with Mac-only data. This is **Component A only** (desktop publish). The iOS read side is a separate plan.

The desktop projection ENGINE already exists (sub-project A, `lib/projection.js`). **We do NOT change the engine.** We only RE-PUBLISH values it already computes, reusing the EXACT same inputs `/api/projection` uses (via the existing `buildLiveProjection(nowMs)` helper in `server.js`) so the snapshot can never drift from `/api/projection`.

## Cross-platform contract — the EXACT published JSON shapes

Two new OPTIONAL top-level keys are added to the snapshot object produced by `buildSnapshot` (in `lib/snapshot.js`). `schemaVersion` STAYS `1` — both blocks are optional; old iOS `JSONDecoder` ignores unknown keys.

### `forecastHistory` (bounded recent slice — hero windows only)

```jsonc
"forecastHistory": {
  "fiveHour": [
    { "at": "2026-06-13T11:32:00.000Z", "pct": 47, "resetsAt": "2026-06-13T15:00:00.000Z" }
    // ... oldest-first, ONLY samples with (nowMs - parseMs(at)) <= RECENT_SPAN_MS (60 min); ~<=12/window
  ],
  "sevenDay": [
    { "at": "...", "pct": 12, "resetsAt": "..." }
  ]
}
```

- ONLY the two hero windows: `fiveHour`, `sevenDay`. No other window keys.
- `pct` is passed THROUGH unchanged — `usage-history.js` stores `win.pct` already in engine units (0–100). **Do NOT rescale.**
- Each sample is `{ at, pct, resetsAt }` exactly as `UsageHistory.samplesByWindow()` emits (no added/renamed fields).
- Degrade: if a window has no recent samples → `[]` (empty array). If `history` is unavailable → both arrays `[]`.

### `forecast` (week-over-week + ROI pace — reused verbatim from the projection)

```jsonc
"forecast": {
  "weekOverWeek": { "deltaPts": -8, "prevPctAtSamePoint": 20 },  // or null
  "roiPace": {
    "trailingDays": 7,
    "apiEquivalentSpendTrailing": 312.40,
    "monthlyEquivalentValue": 1338.86,
    "subscriptionCost": 200,
    "paceMultiple": 5.7
  }  // or null
}
```

- `forecast.weekOverWeek` = `projection.windows.sevenDay.weekOverWeek` (the `weekOverWeek` sub-key the engine attaches to the `sevenDay` window). `{ deltaPts: Int, prevPctAtSamePoint: Int } | null`.
- `forecast.roiPace` = `projection.roiPace` (TOP-LEVEL on the projection result). `{ trailingDays: 7, apiEquivalentSpendTrailing, monthlyEquivalentValue, subscriptionCost, paceMultiple } | null`.
- Degrade (unpaired / no-data): both are `null` (the engine already returns `null` for these when stale / no sessions / sevenDay window absent or not `will_hit|safe`). Publish `forecast: { weekOverWeek: null, roiPace: null }` — never omit the block, never fabricate zeros (phantom-bucket lesson).

## The real reuse path (verified against code — NO drift)

`buildLiveProjection(nowMs)` ALREADY EXISTS at **`server.js:578`** and is the single source of truth feeding both `/api/projection` and `/api/alerts/pending`. It:

1. `record = await usageStore.load()`
2. `history = await usageHistory.samplesByWindow()` — single-pass JSONL read, all WINDOW_KEYS
3. `all = await store.loadAllSummaries()`; `trailing = filterSessions(all, { period:'7d', project:'', now:new Date(nowMs) })`
4. `projection = buildProjection({ normalized: record?.normalized ?? null, ingestedAt: record?.ingestedAt ?? null, history, nowMs, apiEquivalentSpendTrailing: sumSessionCosts(trailing), subscriptionCost: await configStore.effectiveSubscriptionCost() })`
5. returns `{ record, projection }`

`projection` shape (from `buildProjection`, `lib/projection.js:359`): `{ freshness, windows, roiPace }`.
- `projection.windows.sevenDay.weekOverWeek` → the WoW block.
- `projection.roiPace` → the ROI-pace block.

**The enrichment values come straight out of this one call** — same `nowMs`, same spend pipeline, same subscription cost as `/api/projection`. That is the no-drift guarantee.

**One missing piece:** `buildLiveProjection` reads `history` internally but does NOT return it, and `forecastHistory` needs the raw `fiveHour`/`sevenDay` sample arrays. **Decision: extend `buildLiveProjection` to also return `history`** (`return { record, projection, history }`). This keeps ONE JSONL read and ONE `nowMs` for the whole snapshot. (Returning an extra field is additive — `/api/projection` and `/api/alerts/pending` destructure only what they use, so they are unaffected.)


- `now` is ALREADY a param — the handler must pass `now: new Date(nowMs)` so `forecastHistory`'s 60-min filter uses the SAME clock the projection used.
- Inside `buildSnapshot`, after assembling the existing object, add:
  - `forecastHistory: buildForecastHistory(history, now.getTime())` (new local helper, see Task 1).
  - `forecast: { weekOverWeek, roiPace }`.
- `SNAPSHOT_SCHEMA_VERSION` stays `1`. No bump.

### `/api/snapshot` (server.js:650) — new wiring

```js
app.get('/api/snapshot', async (c) => {
  const tz = c.req.query('tz') ?? Intl.DateTimeFormat().resolvedOptions().timeZone ?? 'UTC';
  const nowMs = Date.now();                                   // ONE clock for the whole snapshot
  const { projection, history } = await buildLiveProjection(nowMs);
  const snapshot = await buildSnapshot({
    store,
    usageStore,
    subscriptionCost: await configStore.effectiveSubscriptionCost(),
    tz,
    now: new Date(nowMs),                                     // thread the same clock
    history,
    weekOverWeek: projection.windows?.sevenDay?.weekOverWeek ?? null,
    roiPace: projection.roiPace ?? null,
  });
  return c.json(snapshot);
});
```

> Note: `buildLiveProjection` does its own `store.loadAllSummaries()` (for trailing-7d spend), and `buildSnapshot` does another `store.loadAllSummaries()` (for the headline 30d window + activity). That is TWO loads per snapshot. The loader is cached (`loadAllSummaries`, bounded-concurrency, landmine #38) and `/api/snapshot` is called ~every 300s by the Rust publish loop, so this is acceptable — do NOT refactor the loader to share the result across the two pipelines in this PR (out of scope; would couple snapshot assembly to projection internals). Flag it as a possible later optimization only.

### Task 1 — `buildForecastHistory` recent-slice reader (pure, in lib/snapshot.js)

**Files:** `lib/snapshot.js` (impl), `test/snapshot.test.js` (tests).

**Write first (RED):** new `describe('buildSnapshot — forecastHistory recent slice')` cases. Import `RECENT_SPAN_MS` from `lib/projection.js` in the test to anchor the boundary. Build a fake `history` map and pass it via the `build(..., opts)` helper (`opts.history`). Assertions:
1. **Hero-only:** `Object.keys(snap.forecastHistory).sort()` deepEquals `['fiveHour','sevenDay']` — even if `history` also contains `sevenDaySonnet`, `dailyRoutines`, etc., those keys are NOT in `forecastHistory`.
2. **60-min filter (boundary):** given `fiveHour` samples at `nowMs - (RECENT_SPAN_MS - 1)` (kept), `nowMs - RECENT_SPAN_MS` (kept, `<=`), and `nowMs - (RECENT_SPAN_MS + 60000)` (dropped) → only the two recent ones survive, oldest-first.
3. **pct unchanged:** a sample with `pct: 47` round-trips as `pct: 47` (no /100, no scaling).
4. **Bounded count:** 30 samples all within 60 min → length is whatever passes the filter (≈ all 30 here, but assert it equals the count that passed, and assert the impl does NOT slice to a hardcoded N — the bound is the time filter, not a count cap; spec says "~<=12" is a consequence of 5-min sampling × 60 min, not an enforced cap).
5. **Degrade:** `history: null` → `forecastHistory` = `{ fiveHour: [], sevenDay: [] }`. A window absent from `history` → `[]`.
6. **Shape:** each emitted sample has exactly keys `['at','pct','resetsAt']`.

**Minimal impl:** a module-local helper:
```js
import { RECENT_SPAN_MS } from './projection.js';
const FORECAST_HISTORY_WINDOWS = ['fiveHour', 'sevenDay'];

function parseMs(value) { /* same guard as projection.js: typeof string, Date.parse, Number.isFinite */ }

function buildForecastHistory(history, nowMs) {
  const out = {};
  for (const key of FORECAST_HISTORY_WINDOWS) {
    const samples = Array.isArray(history?.[key]) ? history[key] : [];
    out[key] = samples
      .filter((s) => {
        const atMs = parseMs(s?.at);
        return atMs != null && nowMs - atMs <= RECENT_SPAN_MS;
      })
      .map((s) => ({ at: s.at, pct: s.pct, resetsAt: s.resetsAt }));
  }
  return out;
}
```
(`samplesByWindow()` is already oldest-first file order, so no re-sort needed; `.filter` preserves order.)

## Risks / ambiguities found (code vs spec)

1. **`buildLiveProjection` IS real** (spec named it correctly) — it's at `server.js:578`, returns `{ record, projection }`. The ONLY gap: it doesn't return `history`. The plan extends the return to `{ record, projection, history }` (additive, safe).
2. **`now` vs `nowMs` seam.** `buildSnapshot` takes `now` (a `Date`), `buildProjection` takes `nowMs` (a number). The handler must capture ONE `nowMs = Date.now()`, pass `nowMs` into `buildLiveProjection` AND `now: new Date(nowMs)` into `buildSnapshot`, so `forecastHistory`'s 60-min filter and the projection share one clock. The recent-slice helper converts `now.getTime()` internally.
3. **Double `loadAllSummaries()`** per snapshot (projection's trailing-7d + snapshot's headline-30d). Cached + low-frequency (~300s) → acceptable. Explicitly OUT OF SCOPE to dedupe in this PR (would couple two assembly pipelines). Flag only.
4. **No-drift test timing.** `/api/projection` and `/api/snapshot` are two separate requests with ms-apart clocks. `roiPace` is computed from 7-day spend (clock-insensitive at ms scale) and `weekOverWeek` from sample geometry — both stable across a few ms. If a strict `deepEqual` flakes, fall back to asserting the clock-independent fields (`paceMultiple`, `apiEquivalentSpendTrailing`, `deltaPts`, `prevPctAtSamePoint`). Documented in Task 3.
5. **Size baseline is real-world, not fixture.** The test fixtures build a tiny snapshot (few sessions) far under any ceiling; the 12.4 KB figure is the REAL Mac payload. Anchor the ceiling NUMBER to the real baseline + the documented 1.3–3.3 KB add (→ 18 KB ceiling with headroom), and label it a tightness tripwire, not a correctness gate.
6. **`weekOverWeek` is frequently `null`** in practice (needs ≥2 weeks of history at the right geometry + the sevenDay window in `will_hit|safe` state). The integration test should still assert the no-drift identity even when both sides are `null` — `null === null` is the contract. A separately-seeded non-null case is nice-to-have but the null-identity test is the load-bearing one.
