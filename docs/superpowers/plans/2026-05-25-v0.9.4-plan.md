**Date:** 2026-05-25

## What we're shipping

Three strands bundled because they're complementary and don't share files:

1. **Activity heatmap** (Phase A, ~7-8h) — GitHub-style 7-row × variable-column grid of daily usage intensity. Surfaced in both the dashboard (365d / 180d / All toggleable) and the menu-bar popover (180d, no labels). Builds on the v0.9.1 popover redesign without disturbing it.

2. **Engineering hygiene** (Phase B, ~12-15h) — derived from auditing the TokenTracker (mm7894215/TokenTracker) competitor. Adopts patterns that reduce drift, prevent shipping bugs, and signal professionalism. The eight items are small, mostly parallel, and don't share files with the heatmap.

3. **Opaque-vibrancy treatment** (Phase C, ~1.5-2h) — applies the design handoff in `docs/superpowers/handoffs/2026-05-25-opaque-vibrancy/` to the dashboard window AND propagates the heavier recipe to the popover. Brings both surfaces to CodexBar-style "opaque vibrancy" (wallpaper hue tints faintly through, surface reads near-solid, text always legible).

4. **Dashboard ↔ popover parity fix** (Phase D, ~15min) — surfaced 2026-05-25 by Adnan against the running v0.9.3 build: the dashboard's "EXTRA USAGE" card showed `$— · Temporarily gated by Anthropic` while the popover correctly showed `$19.60 / $10 limit · 196% used`. Dashboard only read `plan.extraUsage` (OAuth-API spend, gated at the org level for many users since 2026-05); popover prefers `plan.consumerOverage` (claude.ai `/overage_spend_limit` — the usage-credits row at claude.ai/settings/usage). Folding the dashboard onto the same preference order.

Combined: one visible feature + visual polish + foundational engineering upgrade + a dashboard parity fix in one release. Heatmap is the user-facing headline; vibrancy is the visual polish; hygiene is the credibility groundwork; the parity fix unblanks a card real users were seeing today.

## Phase A — Activity heatmap (~7-8h)

### A1. `lib/activity.js` — bucketing + streak computation

**What:** Pure module that takes a `{date, sessions, tokens, cost}[]` array and produces:
- Per-day intensity bucket (0 = empty, 1-4 = quartiles of non-zero days)
- `activeDays` (count where `sessions > 0`)
- `currentStreak` (consecutive active days ending today)
- `longestStreak` (longest run of consecutive active days in the period)

**Files:** new `lib/activity.js`, new `test/cli/activity.test.js`
**Effort:** 1.5h
**Acceptance:**
- `computeBuckets([])` returns empty array
- `computeBuckets(allZero)` returns all-zero buckets
- Single-day input doesn't crash quartile calculation
- Streaks correctly handle gaps, today-still-active vs today-empty

### A2. `GET /api/activity` endpoint

**What:** New endpoint on the Hono server that aggregates sessions + claude.ai ingests per calendar day in the user's local timezone. Query params: `period` (default `365d`), `tz` (default system TZ from `Intl.DateTimeFormat().resolvedOptions().timeZone`).

**Response shape:**
```json
{
  "period": "365d",
  "tz": "Asia/Dhaka",
  "today": "2026-05-25",
  "rangeStart": "2026-05-26",
  "activeDays": 192,
  "totalDays": 365,
  "currentStreak": 7,
  "longestStreak": 23,
  "days": [
    { "date": "2026-05-25", "sessions": 4, "tokens": 1230456, "costUSD": 2.41, "claudeAiMessages": 12, "intensity": 3 },
    ...
  ]
}
```

**Files:** edit `server.js` (add route), reuse `lib/activity.js` + `lib/session-store.js` + `lib/usage-store.js`
**Effort:** 30min
**Acceptance:** Endpoint returns valid shape for all three period values + custom tz. CORS unchanged.

### A3. `popover/heatmap.js` — shared renderer (vanilla, no deps)

**What:** Pure renderer. Signature:
```js
renderHeatmap(rootEl, data, options)
// options:
//   variant: 'dashboard' | 'popover'
//   showDayLabels: bool                  // dashboard true, popover false
//   showMonthLabels: bool                // dashboard true, popover false
//   cellSize: number (px)                // dashboard 12, popover 8
//   onHover: (day) => string             // tooltip text
//   onRangeChange?: (newPeriod) => void  // dashboard only

// No palette option — single orange ramp on both variants, defined
```

**Files:** new `popover/heatmap.js`, new `popover/heatmap.css` (orange palette tokens, cell styles, legend)

**Effort:** 2h
**Acceptance:**

- Keyboard nav: arrow keys move focus between cells
- Screen-reader friendly: each cell has aria-label "Sat Mar 15 — 3 sessions"

## Phase B — Engineering hygiene (~12-15h)

Order is approximate effort × ROI. Items don't depend on each other; can be parallelized.

### B1. Copy registry + validator

**What:** Extract all user-facing strings from `popover/popover.js`, `popover/index.html`, and any Rust-side toast/notification text into a single `popover/copy.json`. Strings reference by key: `t("session.elapsed", { hours: 1, minutes: 24 })`. Write `scripts/validate-copy-registry.cjs` that fails CI if it finds hardcoded user-facing strings in those files.

**Files:** new `popover/copy.json`, new `popover/lib/copy.js` (the `t()` lookup function), edits across `popover/popover.js` and `popover/index.html`, new `scripts/validate-copy-registry.cjs`, edit `package.json` (add to `check` script).
**Effort:** 2-3h
**Why:** Foundation for i18n (zh-CN etc.). Single point to review/edit copy. Prevents typo regressions. Validator catches drift.
**Acceptance:** All strings extracted. `npm run check` includes validation. No hardcoded strings remain in scanned files.

### B2. Version-sync validator in release.yml

**What:** Add a step at the top of `release.yml` that asserts `package.json`, `src-tauri/tauri.conf.json`, and `src-tauri/Cargo.toml` all carry the same version AND that version matches the pushed tag (with the `v` prefix stripped).

```yaml
- name: Verify version triple matches tag
  run: |
    TAG_VERSION="${GITHUB_REF_NAME#v}"
    PKG=$(node -p "require('./package.json').version")
    TAURI=$(jq -r .version src-tauri/tauri.conf.json)
    CARGO=$(grep '^version' src-tauri/Cargo.toml | head -1 | cut -d'"' -f2)
    for v in "$PKG" "$TAURI" "$CARGO"; do
      [[ "$v" == "$TAG_VERSION" ]] || { echo "::error::$v ≠ $TAG_VERSION"; exit 1; }
    done
```

**Files:** edit `.github/workflows/release.yml`
**Effort:** 30min
**Why:** TokenTracker shipped a DMG with mismatched Info.plist (v0.5.77 advertised as v0.5.76). Same risk exists in Clauge — three places, no automation. **Counts as a release-pipeline edit per VISION.md** — needs explicit sign-off, same as the homebrew-dispatch wiring in 3eb0e06.
**Acceptance:** Releasing a tag where any of the four versions don't match fails the workflow before the build starts.

### B3. SECURITY.md + CONTRIBUTING.md

**What:**
- `SECURITY.md`: how to report vulnerabilities (email or private GH advisory), what's in scope (Keychain reads, OAuth blob handling), expected response window
- `CONTRIBUTING.md`: required pre-PR checks (`npm run check`), commit-message style (Conventional Commits, no Claude attribution), where to file issues, AGENTS.md landmines pointer

**Files:** new `SECURITY.md`, new `CONTRIBUTING.md`
**Effort:** 30min
**Why:** Professionalism signal. Required cultural artifact for any tool handling credentials (v0.10.0 IAP will sharpen this further).
**Acceptance:** Both files exist at repo root and are linked from the README.

### B4. Self-contained `.app` exposes CLI

**What:** After Clauge installs to `/Applications/Clauge.app`, expose the CLI binary at a predictable path inside the bundle (e.g., `Contents/Resources/clauge-cli`). On first launch, the Welcome wizard offers to install a symlink at `/usr/local/bin/clauge` (with user consent — similar to VS Code's "install `code` command in PATH"). Skipping the symlink is fine; the user can still invoke via the absolute bundle path.

**Files:** edit `src-tauri/tauri.conf.json` bundle resources, new `src-tauri/Resources/clauge-cli` wrapper script, edit Welcome wizard to add the "Install PATH symlink?" step, edit `src-tauri/src/ipc.rs` for the install_cli_symlink command.

**Effort:** 2-3h
**Why:** DMG users currently have no `clauge` CLI unless they also installed via Homebrew. Phase C's CLI was the headline feature of v0.9.3; making it discoverable from the DMG install closes the loop.
**Acceptance:** Fresh DMG install + symlink consent → `clauge config get` works in any terminal. Skipping consent → CLI still callable via `/Applications/Clauge.app/Contents/Resources/clauge-cli config get`.

### B5. Token normalization data contract in AGENTS.md

**What:** New "Load-bearing conventions" section in AGENTS.md documenting:
- How `lib/parser.js` deduplicates JSONL lines by `requestId`
- The cache-tier column shape (`ephemeral_5m` vs `ephemeral_1h`, the `cache_creation` field semantics)
- The cost formula (always recomputed from rates, never read from `costUSD`)
- The "never compute cost from `total_tokens`" warning (TokenTracker hit this; their CLAUDE.md documents it)

**Files:** edit `AGENTS.md`
**Effort:** 1h
**Why:** These conventions are currently implicit. A future agent editing `parser.js` could silently break cost math.
**Acceptance:** New section in AGENTS.md. Cross-referenced from `lib/parser.js` top-of-file comment.

### B6. Native ↔ Web bridge consolidation

**What:** Create `popover/lib/tauri-bridge.js` as the single facade for all `tauri.invoke('...')` calls in the popover/dashboard JS. Each call becomes a typed wrapper:
```js
export const tauriBridge = {
  openClaudeAiLogin: () => invoke('open_claude_ai_login'),
  setProviderEnabled: (name, enabled) => invoke('set_provider_enabled', { name, enabled }),
  // ... one per command
};
```

Then refactor `popover/popover.js` and the Welcome wizard to call `tauriBridge.X()` instead of raw `invoke('x')`.

**Files:** new `popover/lib/tauri-bridge.js`, edits across `popover/popover.js`, Welcome wizard, possibly other consumers.
**Effort:** 3-4h (depends on how scattered the current `invoke` calls are)
**Why:** AGENTS.md landmine #1 (Tauri IPC triple-registration) exists because the surface is scattered. Consolidating to one bridge file makes the registration checklist trivially auditable.
**Acceptance:** Zero raw `tauri.invoke(...)` calls outside `popover/lib/tauri-bridge.js`. Bridge has 1:1 method coverage for every `#[tauri::command]` in `src-tauri/src/ipc.rs`.

### B7. Architecture guardrails validators

**What:** A handful of small CJS scripts that grep the codebase for known anti-patterns:
- `validate-ipc-triple-register.cjs`: for each `#[tauri::command]` in `src-tauri/src/*.rs`, verify it appears in `lib.rs`'s `invoke_handler!`, `build.rs`'s `APP_COMMANDS`, AND `capabilities/main.json`. Missing any = silent IPC rejection (landmine #1).
- `validate-no-console-log.cjs`: no `console.log` in `lib/`, `popover/`, `server.js`. Already a global rule; codify it.
- `validate-no-hardcoded-port.cjs`: no `:3456` literal in `popover/*` — must go through `configPaths.portFile()` / `/api/health`.

**Files:** new `scripts/validate-ipc-triple-register.cjs`, new `scripts/validate-no-console-log.cjs`, new `scripts/validate-no-hardcoded-port.cjs`, edit `package.json` (add to `check` script).
**Effort:** 2-3h (one validator per ~45-60min)
**Why:** Mechanical drift prevention. Catches issues that landmines currently document — turning prose warnings into automated checks.
**Acceptance:** `npm run check` runs all three validators. Each validator has at least one passing + one intentionally-failing test case (the failing case asserts it catches the violation).

### B8. Issue-response cadence note in CONTRIBUTING.md

**What:** One paragraph in `CONTRIBUTING.md` documenting the soft SLA: "We aim to respond to issues within 48 hours, even if it's just acknowledgment. Bugs blocking install or breaking core functionality get same-day attention."

**Files:** edit `CONTRIBUTING.md` (created in B3)
**Effort:** 15min
**Why:** Sets expectations. v0.10.0 IAP changes the user relationship.
**Acceptance:** Paragraph exists. Nothing further to verify.

## Phase C — Opaque-vibrancy parity (~1.5-2h)

Reference materials in `docs/superpowers/handoffs/2026-05-25-opaque-vibrancy/`:
- `HANDOFF.md` — recipe table (the canonical source of truth)
- `README.md` — step-by-step patch instructions (note: the README's patch as-written applies the *lighter* recipe; we want the **HANDOFF.md heavy recipe**, see the table below)
- `Translucent Preview.html` — visual target. Open in a browser before starting.

### Locked recipe (single source of truth)

| Layer | Value |
|---|---|
| Window background | `linear-gradient(180deg, rgba(30, 26, 38, 0.78) 0%, rgba(20, 18, 26, 0.82) 100%)` |
| Backdrop filter | `blur(60px) saturate(180%)` |
| macOS material | `NSVisualEffectMaterial::HudWindow`, `NSVisualEffectState::FollowsWindowActiveState` |
| Brand sheen | `radial-gradient(80% 50% at 0% 0%, rgba(217, 119, 87, 0.06), transparent 60%)` on `body::before` / `#root::before` |
| Card blur (inner glass) | `blur(60px) saturate(180%)` |
| Rim lights | `inset 0 1px 0 rgba(244,236,228,0.10)` (top) + `inset 0 -1px 0 rgba(0,0,0,0.4)` (bottom) |
| Border radius | 14px (window), 18px (cards), 999px (pills) |

Brand color `#d97757` (RGB 217, 119, 87) verified to match `popover/popover.css::--brand` + `public/styles.css::--brand`.

### C1. Dashboard window — vibrancy + transparent builder (Rust)

**What:** Apply `apply_vibrancy(HudWindow, FollowsWindowActiveState, 14.0)` on macOS and `apply_mica` / `apply_acrylic` fallback on Windows to the dashboard window. Add `.transparent(true)` to the `WebviewWindowBuilder` chain so the OS vibrancy layer can paint through.

**Files:** edit `src-tauri/src/windows.rs` — three changes: import line, `.transparent(true)` on builder, `apply_vibrancy` block after `.build()?`.
**Effort:** 30-45min
**Why:** Without this, the dashboard window paints opaque and the new CSS wash has no OS layer to blend into.
**Acceptance:** Dashboard window in `cargo tauri dev` shows wallpaper hue tinting through the corners + edges. No first-paint white flash > 100ms.

### C2. Dashboard CSS — heavy translucent wash

**What:** In `public/styles.css`, replace the current 4-stop opaque gradient on `body { background: ... }` with the heavy linear-gradient + `body::before` brand sheen + bumped `.glass` backdrop-filter.

```css
html, body { background: transparent; }

body {
  /* ... font/color rules unchanged ... */
  background:
    linear-gradient(180deg, rgba(30, 26, 38, 0.78) 0%, rgba(20, 18, 26, 0.82) 100%);
  -webkit-backdrop-filter: blur(60px) saturate(180%);

body::before {

  /* heaviness bump — was 40px/160%, now matches the new recipe */

}
```

**Files:** edit `public/styles.css`
**Effort:** 30min
**Why:** Dashboard parity with the popover's new vibrancy treatment. Wallpaper bleed via `saturate(180%)`; text stays legible because of the 0.78-0.82 alpha.
**Acceptance:** Dashboard cards read crisp against any wallpaper. Brand sheen visible in top-left corner. No layout shift vs current opaque dashboard.

## Phase D — Dashboard ↔ popover parity fix (~15min)

### D1. Prefer `plan.consumerOverage` in `renderFinanceSide`

**What:** Mirror `popover/popover.js::renderExtra` preference order in `public/app.js::renderFinanceSide`. Both surfaces consume the same `/api/usage` payload but the dashboard only ever read `plan.extraUsage`. When Anthropic gates that feature at the org level (`enabled=false, disabledReason='org_level_disabled_until'`) — which they have been doing for many users since 2026-05 — the dashboard's "EXTRA USAGE" card falls into the "Temporarily gated by Anthropic" branch and shows `$—`, even though `plan.consumerOverage` (the claude.ai usage-credits row at claude.ai/settings/usage) is populated with the real spend.

Server already emits both fields (`server.js:518-522`). Popover already prefers `consumerOverage` (`popover/popover.js:399-411`). Only the dashboard was missing the preference.

**Files:** edit `public/app.js::renderFinanceSide` (one function, ~30 lines changed). No test file exists for the dashboard renderer; smoke-test in browser via `npm start`.
**Effort:** 15min (already implemented in this worktree's first commit)
**Acceptance:**
- Dashboard "EXTRA USAGE" card matches popover output when `consumerOverage` has data: `$<used>.00 / $<limit>.00 · <pct>% of cap`
- When `consumerOverage` is absent, fall through to existing branches (`extraUsage.enabled` → spend, `extraUsage.disabledReason` → gated label, else "not configured")
- Bar width clamps to 100% (semantic — bar represents "of cap"); label shows the true pct so a 196% over-cap reading stays visible
- 203 JS + 65 Rust tests still pass

**Why this can't wait for the next planned phase:** It's a visible regression for real users running v0.9.3 today. The fix is one function in one file, fully isolated from heatmap/hygiene/vibrancy work, and ships in the same v0.9.4 bundle.

## Risks & open questions

1. **Popover height after additions.** Heatmap adds ~140px, removed buttons save ~200px — net ~-60px shorter. Should fit under MAX_POPOVER_HEIGHT (1200px). **Mitigation:** smoke-test on a 1024px-tall display.

2. **Range dropdown styling drift on dashboard.** The dashboard's existing period filter is a styled control; the heatmap range needs visual consistency. **Mitigation:** reuse the same select-element CSS class.

3. **Timezone handling.** Activity per "calendar day" depends on user's local TZ. If the user travels across timezones, retrospective day boundaries shift. **Decision:** use the TZ at *render time*, not historical TZ. Document in AGENTS.md.

4. **`/api/activity` performance.** For 365 days of session data, the aggregator scans the full session-store. With a heavy user (1000+ sessions/day), this could be slow. **Mitigation:** add a simple in-memory cache keyed on `(period, tz)`, invalidated on `usageStore.save()`. Defer until measured slow.

5. **Tauri IPC triple-register validator (B7) is non-trivial.** It needs to parse Rust source enough to extract `#[tauri::command]` names — naïve regex works for current code style but could break on macros. **Mitigation:** start with a strict regex that requires the exact `#[tauri::command]` line above the function. Document the constraint.

6. **Architecture guardrails risk false positives.** A validator that's overly strict creates noise. **Mitigation:** allowlist mechanism per script (a JSON file of intentional exceptions). TokenTracker's `SDK_ALLOWLIST` pattern in their validator is a good reference.
